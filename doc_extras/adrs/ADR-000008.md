# ADR-000008: A Node Is Its Name — an Owner-Issued Incarnation Orders Its Specifications

- **Status:** PROPOSED
- **Decision:** Every peer-service manager identifies a node by its name alone, and orders the node specifications of one name by an `incarnation` number that only the node itself issues.
- **Origin:** Proposed in part by the reporter of [lasp-lang/partisan#270](https://github.com/lasp-lang/partisan/issues/270), whose option A (a revision in the specification) this record adopts in a specific form. The reporter also found the connection-count defect that clause 8 addresses.

## Context

A node specification (`partisan:node_spec()`) carries an identity, `name`, and a location, `listen_addrs` and `channels`. Callers and `partisan_peer_connections` identify a node by its name. The membership structures identify it by the whole specification:

- the pluggable manager's `partisan_membership_set` is a `state_orset` of specifications;
- the HyParView active and passive views, and its `sent_message_map` and `recv_message_map`, are keyed by specification;
- the static and client-server managers keep a `sets:set()` of specifications.

When a node returns on a new address, or changes address while it runs, one name has two specifications. Nothing in a specification says which one is newer, so each manager has to guess. The pluggable manager guesses by liveness: `partisan_peer_service_manager:is_stale/1` calls a specification stale when its node is connected, but not through any of its addresses. The HyParView manager keeps both. The static manager's `update_members/1` ignores a specification whose name it already knows.

The HyParView paper identifies a node by its address, "a tuple (ip, port) that allows a node to be reached" (Leitão, Pereira and Rodrigues, 2007). In the paper, a node that changes address is a failed node followed by a new one. Partisan names nodes, so it can do better, but it has to keep the paper's view rules: symmetric active views, TCP as the failure detector, and passive views that may hold stale entries.

## The decision

1. **A node's identity is its name.** The pluggable membership is a set of names. The HyParView views, and its message-id maps, are maps from name. The static and client-server memberships are maps from name to specification.
2. **A node specification carries `incarnation`,** a non-negative integer. Only the node the specification describes changes it.
3. **Of two specifications with one name, a manager keeps the one with the higher incarnation.** A specification without `incarnation` counts as incarnation 0. Liveness takes no part in the choice.
4. **A node takes `max(Persisted + 1, erlang:system_time(microsecond))` as its incarnation at boot.** `Persisted` is the last value saved under `partisan_data_dir`, if any. The node adds 1 on each change to its own `listen_addrs` while it runs. Leaving a cluster does not delete the saved value.
5. **A node that receives its own name with an incarnation greater than or equal to its own** sets its incarnation one higher and announces its specification again.
6. **Every path by which a specification arrives applies clause 3 through one function.** For HyParView these are `join`, `forward_join`, `neighbor`, `neighbor_request`, `neighbor_accepted`, `shuffle`, `shuffle_reply`, `disconnect`, the X-BOT messages, and `update_members/1`. For the pluggable manager they are `join/1`, `update_members/1` and the membership merge. For the static manager they are `join/1` and `update_members/1`; for the client-server manager, `join/1`. Each path also applies the connection handshake of clause 9.
7. **Choosing the specification for a name does not change which names a view holds.** A newer specification for a name in a view replaces the held one in place. It does not change the view's size, evict a third party, or send a `disconnect`. Which names enter and leave a view stays each manager's own policy: for HyParView, the paper's join, priority and shuffle rules, and X-BOT's optimisation.
8. **A manager that adopts a higher incarnation dials the new addresses first, then closes its connections on every address the new specification does not list.** If no connection to the node remains, the manager's failure handling applies, as for any lost connection.
9. **Both ends of a connection present their own specifications in the handshake,** and so declare support for incarnations. To a peer that has not declared support, a node sends specifications without `incarnation`, and membership in today's gossip format.
10. **A specification without `incarnation` that the application supplies is a contact, not a claim.** This covers `join/1`, `update_members/1` and discovery. The manager connects to its addresses and admits the specification that the peer presents in the handshake.
11. **The HyParView epoch is the node's incarnation.** A manager that adopts a higher incarnation for a peer resets that peer's entries in `sent_message_map` and `recv_message_map`.

## Rationale

- **Liveness is not freshness.** A live address does not make a specification newer. A half-open connection on the old address, plus one failed attempt on the new address, makes `is_stale/1` true for the new specification, and the pluggable manager prunes it. This was shown on v6.3.3 by driving the attempt-failure handler. With a connection on the old address, the new specification leaves the membership; without that connection, it stays. A node that never connects to the new specification cannot call the old one stale, so convergence depends on every holder connecting. The full mesh provides that; HyParView's partial views do not.
- **One writer makes merge trivial.** Only the owner writes its incarnation, so no two writes conflict. Merge is `max`, a join-semilattice. It is a valid CRDT merge for the pluggable gossip, beside the `state_orset` of names, and a total order for the other managers.
- **The boot floor removes the restart window.** A node without a durable `partisan_data_dir`, such as a container without a volume, loses its counter on restart. With the wall-clock floor, the new instance starts above every value its previous instance issued. The floor assumes that a restarted instance's clock is not behind the previous instance's clock by more than the restart took. With a durable `partisan_data_dir`, `Persisted + 1` holds without that assumption.
- **Refutation covers a broken clock assumption.** It is the mechanism of SWIM (Das, Gupta and Motivala, 2002). With the floor, it is expected to fire rarely.
- **One admission function, because every path is a replay source.** The reporter showed that `update_members/1` reaches HyParView's `merge_exchange/2`, which removes only exact matches of the active view. A new specification for an active name therefore lands in the passive view beside the old one. X-BOT messages carry the specifications of up to four nodes: initiator, old, candidate and disconnected (Leitão, Marques, Pereira and Rodrigues, 2009). A path left out keeps the defect.
- **The paper's view rules stay intact, because clause 7 separates choice from membership.** The paper's guarantees come from its rules for adding, dropping and promoting nodes. A change of address is not one of those events, so it must not trigger them. Passive views keep the paper's tolerance of stale entries. A passive entry that fails to connect is removed (§4.3), and shuffles spread the higher incarnation (§4.4).
- **A newer specification does not retire old connections, so clause 8 does.** Name-keyed membership changes which specification a manager holds, not which connections exist. In v6.3.3, `partisan_peer_connections:dispatch_pid/3` selects a connection by name, whatever its address, so a half-open connection on a dropped address keeps carrying traffic. It also keeps counting. `partisan_peer_service_manager:connect/2` tries each listen address, but checks parallelism with `partisan_peer_connections:count/2`, which counts connections on any of the specification's addresses. When a specification lists the old and the new address, connections on the old one fill the parallelism, and the new address is never dialled. This is established by reading the v6.3.3 source; no test exercises it yet. Dialling first keeps a HyParView active-view link up across the change, so the change does not look like a failure under §4.3.
- **An older node cannot simply ignore the key, so compatibility needs clause 9.** Shown on v6.3.3: when a node restarts on the same address, its two specifications differ only in `incarnation`. Both are connected, so neither is stale, and both stay in the membership. `members/0` then lists the node twice, once per restart. A new membership format also fails, because `partisan_full_membership_strategy:handle_message/2` accepts only a `#full_v1{}` state. With clause 9, an older node sees what a v6.3.3 node sends today.
- **Only the owner knows its incarnation, so the application cannot supply one.** Discovery and configuration know an address, not a life of the node. Under clause 3 alone, a specification from discovery, at incarnation 0, could never replace a held one. The handshake is the one place where the node speaks for itself. The client already checks that the server's `hello` names the expected node (`partisan_peer_service_client:handle_inbound/2`). Clause 10 makes that exchange carry the specification. For the static and client-server managers, which have no gossip, the handshake is also how a moved node announces itself.
- **Two monotonic counters per node are one too many.** The HyParView epoch orders disconnect ids across a node's lives. It is loaded from `partisan_data_dir`, so without one it is 1 on every boot (`zero_epoch/0` and `init/1`), and a restarted node's disconnect ids compare as old. The incarnation is monotonic across lives by clause 4, so it serves as the epoch. A peer's new incarnation is a new life of that peer, which cannot have seen the ids of the old one, so its entries reset.

## Alternatives considered

- **Replace a held specification only when it has no connected address** (option B in #270). Rejected as the decision: it is the liveness rule above, with its failure to tell a replay from a change.
- **An optional revision, with the liveness rule as fallback** (option C in #270). Rejected: the fallback keeps the liveness rule's failure modes.
- **A pure logical clock, recovered from peers after a restart without disk.** Rejected: until the node hears its old specification, every node that holds it rejects the new one, and with partial views the node may never hear it.
- **Erlang distribution's `creation`.** Rejected as a model: it only has to differ from the previous value, because a local epmd decides which instance is current. Partisan has no such authority.
- **The paper's model: an address change as a failure followed by a join.** Rejected: every holder of the old address treats the node as failed. Its active-view links then churn, and its passive entries are lost until shuffles bring the new address. A named node can keep its links.

## Consequences

- **Stale-specification pruning goes away.** `is_stale/1`, public since v6.3.3, is deprecated and later removed.
- **A specification with additional `listen_addrs` is adopted at once**, and a replayed old specification cannot replace a newer one.
- **Roaming becomes possible:** a node that detects an address change updates `listen_addrs` and its listener, increments its incarnation and announces itself. ADR-000009 decides the local operation that does this. Detecting the change is outside both records.
- **Each manager announces a change in its own way:**
  - the pluggable manager gossips its own entry;
  - HyParView sends `neighbor` to its active view, and lets shuffles carry the change to passive views;
  - the static and client-server managers reconnect, and the handshake of clause 9 carries the change.
- **The pluggable manager's persisted membership changes format** and needs a migration on load.
- **The handshake changes.** Today's `hello` carries only the node name and the channel, so a node cannot tell whether a peer supports incarnations. A mixed-version test has to show that a mixed cluster behaves as v6.3.3 does.
- **The static manager's `update_members/1` follows address changes.** It stops ignoring a known name, because clause 10 dials the contact.
- **Tests have to show:**
  - **clause 8:** a specification lists the old and the new address, and connections on the old one fill the parallelism. Then a higher incarnation without the old address is adopted. The test asserts that the new address is dialled, the old connections close, and a HyParView peer stays in the active view;
  - **clauses 6 and 7:** for each HyParView path, a replayed old specification leaves the views unchanged, and a newer one replaces the held one without changing the view's size;
  - **clause 11:** a peer that restarts without `partisan_data_dir` can rejoin the active view of a node that had sent it a `disconnect`.
- **An incarnation is as trustworthy as the gossip that carries it.** A peer that can inject membership can claim a name with a high incarnation, as it can inject a specification today. ADR-000005 governs which peers can send membership.
