# ADR-000009: One Owner for a Node's Own Specification, Changed by One Operation

- **Status:** PROPOSED
- **Decision:** One process owns a node's own specification, and `partisan_peer_service:move/1` is the only operation that changes its addresses while the node runs.
- **Origin:** Proposed by the reporter of [lasp-lang/partisan#270](https://github.com/lasp-lang/partisan/issues/270) as the local half of roaming, including `move/1`, its bound and advertised addresses, its meaning of `ok`, and the boot rule. This record adds the order of steps, the failure behaviour, and the case without `partisan_data_dir`.

## Context

A node's own specification exists in three holders, and each takes its value at a different time:

- `partisan_config:set/2` writes `listen_addrs` to the application environment and to `persistent_term`. `partisan:node_spec/0` rebuilds the specification from them on every call.
- The HyParView manager calls `partisan:node_spec/0` once in `init/1`, keeps the result in its state and in its active view, and sends that copy in `join`, `neighbor`, `forward_join` and `shuffle` messages.
- `partisan_acceptor_socket_pool_sup:init/1` reads `listen_addrs` once and builds one listener per address. Each listener binds its address for its lifetime. A listener bound to port 0 writes the assigned port back with `partisan_config:set/2`.

A write to the configuration reaches only the first holder. To change its address today, an application writes the configuration, restarts the listener supervisor, and asks the manager to re-read its specification, in that order. The order matters: a peer admits a neighbour only if it can connect back to it, so a specification announced before its listener is up is rejected.

## The decision

1. **One process, the owner, holds the node's committed specification.** It runs under `partisan_sup` and starts before the listeners and the peer-service manager. It publishes the committed specification in `persistent_term`, and `partisan:node_spec/0` returns that value.
2. **No other process copies the specification.** The managers call `partisan:node_spec/0` each time they send their identity. The listener pool binds the addresses the owner gives it, and the owner records the port a listener is assigned.
3. **`partisan_peer_service:move(#{listen_addrs => Advertised, bind_addrs => Bound})` changes the node's addresses.** The caller supplies the addresses, and Partisan issues the incarnation (ADR-000008). `bind_addrs` defaults to `listen_addrs`. When the two differ, every advertised address carries an explicit port.
4. **`move/1` takes its steps in this order:**
   1. bind listeners on `Bound`;
   2. save the specification;
   3. publish it;
   4. call the manager's change callback;
   5. close the listeners on addresses no longer in `Bound`.
5. **`move/1` returns `ok` when the manager's callback returns.** `ok` says nothing about any peer. Each manager announces the change as ADR-000008 describes.
6. **A failure before step 3 changes nothing.** The owner closes the listeners it opened in step 1 and returns `{error, Reason}`. The node keeps its committed specification and its listeners.
7. **`move/1` does not close connections accepted on old addresses.** A peer closes them after it reaches the new address (ADR-000008, clause 8). A connection on an address that no longer exists ends with the address.
8. **The owner saves the specification together with the configuration it replaced.** At boot, the owner compares the saved configuration with the current one:
   - if they are equal, it binds the saved addresses;
   - if binding the saved addresses fails, or the configurations differ, it binds the configuration's addresses.
9. **Without `partisan_data_dir`, a move does not survive a restart.** `ok` then means steps 1, 3 and 4 have completed, and at boot the configuration's addresses apply. The incarnation still increases across restarts, by ADR-000008, clause 4.
10. **After boot, `partisan_config:set(listen_addrs, _)` returns an error.** `partisan_config:get(listen_addrs)` returns the committed value.

## Rationale

- **Three holders make three operations.** With one owner, a change takes one operation, and the wrong orders that exist today cannot be performed.
- **The order of steps follows the receiving side.** A peer admits a neighbour only if it can connect back. Binding before publishing means no peer learns an address that refuses connections. Closing old listeners last keeps the node reachable while peers move.
- **The specification is read often and changed rarely, so `persistent_term` fits.** A read costs no message to the owner. A write affects every process that holds the old term, which is acceptable for a change of address.
- **The pull model removes cache invalidation.** A manager that reads the specification each time cannot hold a stale copy. The callback in step 4 tells the manager to announce, not what to send.
- **All-or-nothing up to publication** makes `{error, Reason}` mean the node is as it was. After publication a peer may already have the new specification, so there is nothing safe to undo.
- **Peers close old connections, because they know when they are ready.** If the moving node closed accepted connections at once, every HyParView peer would lose its link before it could dial the new address. Under §4.3 of the HyParView paper, each peer would then treat the node as failed.
- **Bound and advertised addresses differ behind NAT and in containers.** A node listens on one address, and peers reach it on another. Behind NAT, a port assigned to a port-0 listener is not the advertised port, so the advertised port has to be explicit.
- **Boot must not undo a move, and a saved move is evidence, not a promise.** If the saved move always won, a changed deployment would be ignored. If the configuration always won, every restart would undo a move. Saving the configuration that the move replaced tells the two cases apart. A saved address that can no longer be bound shows where the node was, not where it is.
- **Durability needs disk.** Without `partisan_data_dir` there is nowhere to save a move. The application's detector runs at boot as it runs at runtime, so it moves the node again.
- **One writer for `listen_addrs`.** A configuration write that bypasses the owner would bring back the disagreement this record removes.

## Alternatives considered

- **Re-read the configuration on request** (`refresh_node_spec`, proposed in #270 for the HyParView manager). Rejected: it keeps the configuration as the authority, and it leaves the listener to the caller. Re-reading before the listener is rebound is the unsafe order.
- **Notify the managers of every change and let them cache it.** Rejected: a cache needs invalidation, and each manager would implement it.
- **Detect address changes inside Partisan.** Rejected for this record: the advertised address cannot be derived from local interfaces behind NAT or a service address. `partisan_inet` reports only whether a non-loopback interface exists. A detector for the case where advertised and bound addresses are equal could be a later, optional addition.

## Consequences

- **The HyParView manager stops caching its own specification**, including its own entry in the active view. The listener pool stops reading `listen_addrs` in `init/1`.
- **The peer-service manager behaviour gains a change callback.** Every manager implements it.
- **Roaming becomes an application that detects an address change and calls `move/1`.** Detection, and announcements to discovery services such as mDNS, stay with the application.
- **`partisan_config:set(listen_addrs, _)` after boot stops working.** Applications that call it, as the #270 workaround does, move to `move/1`.
- **Tests have to show:**
  - a peer receives the new specification only after the new listener accepts connections;
  - a failed bind leaves the node's specification and listeners unchanged;
  - a restart with an unchanged configuration keeps the saved move, and a restart with a changed one does not.
