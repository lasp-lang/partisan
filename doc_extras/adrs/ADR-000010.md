# ADR-000010: A Peer's Name Is a Binary Until the Local Node Converts It

- **Status:** PROPOSED
- **Decision:** Partisan carries a peer's name as a binary on the wire and in its membership state, and only the local node's own code, never the decoder, creates the atom for it.

## Context

The runtime never collects an atom, and by default it holds at most 1,048,576 of them (Erlang/OTP system limits). Partisan decodes every frame with `binary_to_term/1`, and a node specification carries `name` as an atom, so each name that a frame mentions becomes an atom on the receiver. ADR-000005 puts authentication ahead of that decoder. It leaves the decoder, and the name type, as they are for a connection that has authenticated.

## The decision

1. **Every frame of Partisan's own protocols carries a node name as a UTF-8 binary.** This covers the handshake, `ping` and `pong`, the membership gossip, and the messages of each peer-service manager. It covers the `name` of every node specification those frames carry.
2. **Membership state holds names as binaries.** The name-keyed structures of ADR-000008 use the binary as the key. So does the membership that the pluggable manager saves under `partisan_data_dir`.
3. **One function converts a peer's name to an atom.** A manager calls it when a name crosses from membership state to the connection table or to a caller. No other code path creates an atom from a peer's name.
4. **The public API keeps `node()`.** A function that takes a name accepts the atom and converts it with `atom_to_binary/1`. `partisan_peer_connections` stays keyed by atom, so sending a message converts nothing.
5. **Both ends declare support for binary names in the handshake of ADR-000008.** To a peer that has not declared support, a node sends names as atoms.

## Rationale

- **Nothing in the runtime needs a peer's name as an atom.** Partisan dials the addresses in a specification's `listen_addrs` and never asks epmd or `net_kernel` to resolve a name. The calls that need an atom are `erlang:monitor_node/3`, `net_kernel:monitor_nodes/2`, `net_kernel:disconnect/1` and `erlang:nodes/1`. Each sits behind `connect_disterl = true`, which is off by default. Established by reading `partisan`, `partisan_peer_service_manager` and `partisan_util`.
- **A binary name is what lets a node decode with `safe`.** `binary_to_term(Data, [safe])` refuses a frame that names an atom the node does not hold. A joining node's name is such an atom. A probe on OTP 29 decoded a hand-built frame that named an unknown atom, alone and nested in a tuple and a list. The call failed with `badarg` and the atom count did not change. The same name as a binary, under a tag the node holds, decoded.
- **Today the sender decides which atoms the receiver holds.** `partisan_membership_set:decode/1` and the frame handlers of `partisan_peer_service_server` and `partisan_peer_service_client` call `binary_to_term/1`. A name in a gossiped specification becomes an atom on every node the gossip reaches, whether or not that node ever connects to the peer.
- **Honest clusters also grow the atom table.** A node without a configured name generates one from a UUID at each boot (`partisan_config`, `gen_node_name/0`). Each restart of such a node adds one atom to every node that learns the name.
- **One conversion function makes the growth local and countable.** The local node decides when to convert, so a limit or a telemetry event has one place to live. This record adds neither.
- **The connection table stays keyed by atom because sending is the hot path.** `partisan:forward_message/3` takes an atom and finds the connection by it. A binary key would add a conversion to every send.

## Alternatives considered

- **Binary names in the public API.** Not decided here. It removes the atom for a peer altogether, and it breaks every caller: `partisan:node/0`, `partisan:nodes/0`, `partisan_peer_service:members/0` and `{Name, Node}` destinations all use `node()`. With `connect_disterl = true` the name has to be an atom. After this record, that change touches the API boundary only.
- **`binary_to_existing_atom/2` at the boundary.** Rejected: with partial views a node legitimately meets a name it has never held. `partisan_remote_ref` records the same reason in its source.
- **Keep atom names and decode the whole stream with `safe`.** Rejected: a node cannot decode the name of a peer that joins.
- **Keep atom names and cap the membership size.** Rejected: the cap bounds the membership, not the decoder. A frame creates its atoms before any code can count them.

## Consequences

- **The wire format changes.** A mixed cluster relies on clause 5. A test has to show that a node that supports binary names and one that does not exchange membership as v6.3.3 nodes do.
- **Protocol frames can be decoded with `safe`.** Doing so needs a frame format that separates Partisan's own messages from application payloads. Today one clause of `handle_inbound/2` forwards both to the manager. That format is a separate decision.
- **Atoms still accumulate, one per name the local node converts.** In a full mesh a node connects to every member, so it converts every name it learns. A cluster of nodes with generated names keeps growing the atom table until the API carries binaries.
- **A remote reference still carries an atom.** The `tuple` and `improper_list` values of `remote_ref_format` put the node name in the application payload as an atom. The `uri` value carries a binary. This record does not change `partisan_remote_ref`.
- **This record does not defend against a hostile peer that has authenticated.** `partisan_rpc_backend` applies the module, function and arguments that a connected peer sends. ADR-000005 decides which peers connect.
- **The saved membership changes format** and needs a migration on load, the same one ADR-000008 requires.
- **The authentication frames of ADR-000005 need no special case.** They already carry the name as a binary, and the conversion of clause 3 runs after the handshake completes.

## Related records

- **ADR-000005** — authenticates a peer before any frame reaches the decoder, and carries binary names in its own frames. This record extends that representation to the rest of the protocol.
- **ADR-000008** — keys membership by name and defines the handshake in which both ends present their specifications. This record sets the type of that name and uses that handshake to declare support.
